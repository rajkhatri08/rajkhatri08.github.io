Thesis

AI you can audit

I work on retrieval and reasoning systems that can be audited — where the useful question isn’t “did the model answer?” but “can we show where that answer came from, and was that source still valid?”

That framing didn't come from AI. It came from a weld shop at Tata Motors, where I traced a long-standing defect with regression analysis and then went and measured the parts by hand before presenting it, because a finding that hasn't survived contact with the physical world isn't a finding yet. A model that agrees with itself proves nothing.

Applied to AI, that instinct has produced three deployed systems. The newest goes back to where it started: a plant-health agent that catches chemical-plant faults early, points to the equipment behind them, and proposes a root cause only when the evidence supports one — with a supervisor approving before anything happens. Before it came Source-Governed RAG, where a lapsed or unapproved source can veto an otherwise perfect semantic match, and a supplier quality agent that decides, per question, whether the answer lives in structured defect data, in corrective-action documents, in both, or in neither — and declines rather than guessing when it’s the last one.

Alongside them is the unglamorous half — I build backend for a live product, so schema design, auth, migrations and deployment aren't theory. Most GenAI prototypes die on the way to production. I've shipped the part that usually kills them.

01The problem

In a chemical plant, faults often start small and hide behind control loops. Operators get flooded with alarms, and finding the root cause takes hours.

And around toxic chemicals and high pressure, an AI that acts on its own isn’t acceptable.

02What I built

  1. DetectWatches all 33 measurements together — static PCA, with T² and SPE combined into one ratio
  2. LocatePoints to the equipment section behind the alert, from reconstruction-based contributions
  3. MatchChecks the evidence against a governed library of 12 failure modes — best fit, or decline
  4. ExplainA LangGraph agent makes one Gemini call to explain the pick, break ties or veto it
  5. VerifyA deterministic faithfulness check verifies every cited fact and action
  6. ApproveA supervisor approves before anything happens

The detector raises one plant-level alert, calibrated to about one false alert per day, with a quieter Watch band before it. Library entries are versioned, with approval gates and entry tests. The system never touches plant controls.

An emergency screen runs before any model call, and a 36-case safety set tests prompt injection, unsafe requests, fake authority and emergencies.

03How I tested it

On the Tennessee Eastman process benchmark (the Rieth et al. dataset), split by run number into fit, calibration, dev and a sealed test set.

Every setting, threshold and command was fixed and tagged in git before the sealed test set was opened. The test ran once, and every data access was logged. Results carry 95% bootstrap intervals, and an independent check reproduced published detection rates (Yin et al., 2012) within 10 points on 11 of 12 faults.

05What didn’t work

  • The LLM layer cost accuracy. On the sample used to test it, it cut top-1 by 3.8 points (66.1% against the matcher’s 69.9% on that same sample), so the pre‑registered rule said not to let it re‑rank. It also over-declines known faults: 27%, against the matcher’s 13%.
  • A random forest beat my matcher. The baseline reached 87.0% top-1 against 75.7%. The matcher ships because every proposal traces to named evidence.
  • The plant is simulated. A real one would add sensor drift, missing data and batch operation.

06What I’d do next

  • A pilot on real plant data — read-only, past data from one unit.
  • A batch-aware detector for batch reactors.
  • A prompt fix so that only required evidence can rule out a cause.

Deployed · Agentic retrieval

An agent that decides, then declines

Supplier Quality Risk Agent — routes a supplier question to structured defect data, to corrective-action documents, to both, or to neither. The last option is the one that matters.

Live · DeployedSep 2026 · 16 days · 11 phases
88–92%Routing accuracy on a pre‑registered 24-question set, reported across five runs
Try the agent Code API docs

Python · FastAPI · Gemini · Postgres + pgvector · Render · Neon · Vercel · synthetic data, no proprietary records

Each query gets one routing decision before any tool runs, and the decision is surfaced above the answer so a reviewer reads the system's reasoning first. Four tool failure modes are modelled separately, so “this supplier does not exist” and “I could not check whether it exists” never collapse into the same empty result.

How it was built 6 decisions
  1. Pre-registering the answer key

    I committed the routing ground-truth rule and the labelled 24-question evaluation set to version control before writing the router, so the reported accuracy couldn't be quietly fitted to whatever the system turned out to do. Routing went from a 75% baseline to 88–92% through two measured prompt changes, with the before-and-after score recorded in each commit message.

  2. Reporting a range, not a best run

    Three of 24 questions flipped between runs, worth 4.2 percentage points each, so the headline figure is a range across five runs rather than the best one. Two evaluation questions turned out to be mislabelled and I corrected them with written reasoning. A third failure I left counted as a miss, because fixing it needed a real system change rather than a relabel.

  3. Refusing the impressive option

    Text-to-SQL passed a pre-registered 25-question reliability spike at 25/25 — and I rejected it anyway, because one query reached a correct answer by an unsound method. It was replaced with a fixed catalogue of eight parameterised queries: less question coverage, but every path is reviewable. In a system where a wrong number triggers a supplier corrective action, that trade is worth making. SQL injection is eliminated structurally through driver-level parameter binding rather than input sanitisation.

  4. Catching it inventing evidence

    A prompt improvement introduced a regression: the router began fabricating evidence for a supplier that doesn't exist. Constraining the prompt with the real entity list took decline accuracy to 5/5. Separately, the trace layer revealed five of six retrieved passages coming from the wrong supplier's report — a defect that passage counts alone had completely concealed.

  5. Data built to be falsifiable

    A reproducible 24-month synthetic dataset — 10 suppliers, 50 parts, 4,725 defect events, 13 reports — with five deliberately planted patterns providing verifiable ground truth. It includes a paired case where two suppliers show statistically identical defect-rate increases requiring opposite responses: one a genuine process degradation, one a measurement artefact. That makes single-source failure demonstrable rather than theoretical.

  6. Running it in production

    Deployment footprint cut 78%, from 476 MB to 107 MB, by migrating vector storage from ChromaDB to Postgres pgvector against a 512 MB platform limit — verified behaviourally by re-running the retrieval suite and confirming cosine distances matched to four decimal places. Routing and execution are split across separate endpoints so the decision surfaces seconds before tool results complete. Git history was audited for exposed secrets before open-sourcing.

Deployed · RAG & governance

Governed RAG: an answer you can audit

Source-Governed RAG — a retrieval system over regulatory documents where a source's approval status and review date can veto an otherwise perfect semantic match.

Live · DeployedAug 2026 · design through deployment
78→95%Retrieval accuracy after replacing fixed-size chunking with document-structure chunking
Open the dashboard Backend Dashboard

Python · FastAPI · ChromaDB · PostgreSQL · Next.js · MiniLM embeddings via ONNX runtime · three services

Governance overrides ranking: the closest semantic match (0.94) is refused because its source has expired, and a lower-scoring but currently approved regulation is used instead.

THE FAILURE MODE

Semantic search will confidently answer from an expired internal policy if it happens to be the closest match. I reproduced exactly that: a lapsed document outranking current regulation on similarity, returning a deadline that would place an organisation in breach.

So approval status and review date are enforced as a veto, not a weighted score — a strong semantic match cannot outrank a failed trust check. Results tier gold, silver, bronze; the best-scoring match in the whole evaluation set is still bronze, because its source was never approved.

How it was built pipeline + 4 decisions

Six-stage query pipeline — ingest, embed, retrieve, govern, generate, audit. Governance and audit are enforced stages rather than post-hoc checks; each stage is independently testable and every response carries its own provenance.

  1. Retrieval quality

    Accuracy went from 78% to 95% on the labelled set by replacing fixed-size character chunking with document-structure chunking. I found the cause by reading the retrieved text rather than tuning prompts: character windows were truncating enumerated legal clauses before the subsection containing the answer. Regex lookahead splitting now keeps whole provisions with their headings intact.

  2. Evaluation

    A 23-question hand-labelled set, deliberately small and adversarial rather than broad. It spans answerable, out-of-corpus and conflicted cases, with plausible negatives built to provoke false confidence. It's an edge-case audit, not a scale benchmark, and the accuracy figures should be read that way; the next step is running it against a larger uncurated corpus.

    Within that set I swept 70 similarity thresholds, measured a 73.9% accuracy ceiling for distance-based confidence, and removed the feature rather than ship an unreliable signal. Grounding was verified by querying a fact the model knows but the corpus doesn't, and confirming refusal.

  3. Audit trail

    Every request writes timestamp, tier, reasoning, sources, distances and warnings to PostgreSQL. Any decision is reconstructable months later. Document text lives on disk; all governance state lives in the database, giving one source of truth for trust decisions. The service exposes six FastAPI endpoints with schema validation and generated OpenAPI docs.

  4. Running it in production

    First deploy failed: 2 GB of GPU libraries on a 512 MB instance. Swapping to an equivalent ONNX runtime cut the footprint by roughly 96%, verified behaviour-identical before shipping. Evaluation runtime went from 4.5 minutes to 2 seconds through result caching keyed to invalidate on configuration change. Audit logging moved off the filesystem to PostgreSQL, because ephemeral instances erase runtime writes on restart. Infrastructure failures are also separated from model refusals, so a provider outage can't corrupt an accuracy measurement.

Where the habit came from

Grounding, before it was an AI problem

Before I applied it to retrieval, I had to prove a statistical claim against physical reality on a factory floor. Same discipline, different medium: a falsifiable hypothesis, an explicit method, and an external check the model can't fake.

Why this sits on a GenAI portfolio: retrieval grounding and root-cause diagnosis are the same discipline. Both start from a claim that looks convincing, and both are only worth anything once something outside the system — a gauge, a cited source — agrees with it. The plant-health agent in section 02 automates the hypothesis step of this same process, and still asks a person before anything happens.

TATA MOTORS  ·  INDUSTRIAL TRAINEE — DATA ANALYTICS  ·  JUL–AUG 2026  ·  PANTNAGAR, UTTARAKHAND  ·  BODY-IN-WHITE QUALITY

01 — PROBLEM

A long-standing body-in-white quality issue in the weld shop. No labelled dataset, no schema — inspection records collected for compliance, not analysis.

02 — METHOD

Linear regression with R² confidence scoring on the inspection records, with every hypothesis falsifiable by design: if a cause on the line were responsible, the pattern would track time on the line. The regression's job was to rule causes in or out, not just describe the data.

03 — VALIDATION

Before presenting anything, I measured the parts physically on the line, and the gauge agreed with what the regression predicted. A model that agrees with itself proves nothing; this one had to agree with a gauge.

04 — DELIVERY

A containment procedure that needed no production stoppage, a dashboard for ongoing quality monitoring, and a technical report benchmarked against DFMEA and Six Sigma.

I then presented the findings to plant leadership and quality stakeholders, and defended the method under questioning — including alternative explanations I had already tested and ruled out. Translating a statistical result into a decision a cross-functional plant team would act on was as much of the work as the analysis.
